Predicados em SQL & Contratos de Código (DbC)

A formalização da Lógica de Predicados em Bancos de Dados Relacionais (WHERE, EXISTS, HAVING) e na Engenharia de Software com Design by Contract (Pré-condições, Pós-condições e Invariantes).

1. A Cláusula WHERE como Função de Verdade e Conjunto Verdade

Em bancos de dados relacionais (RDBMS), uma tabela é uma relação matemática formal: um subconjunto do produto cartesiano dos domínios de seus atributos. Cada linha da tabela é uma tupla t.

O domínio de discurso U é o conjunto de todas as tuplas da tabela. A cláusula WHERE nada mais é do que uma função proposicional / predicado p(t). Quando o motor relacional processa uma consulta, ele calcula exatamente o Conjunto Verdade Vp:

SELECT * FROM Clientes WHERE saldo > 1000 AND status = 'ATIVO';
Vp = { t ∈ Clientes | (t.saldo > 1000) ∧ (t.status = 'ATIVO') }
AND, OR, NOT ⇔ Conjuntos

AND opera a interseção de tuplas (Vp ∩ Vq). OR opera a união (Vp ∪ Vq) e NOT calcula o complemento por diferença de conjuntos (U — Vp).

Quantificadores em SQL

EXISTS implementa diretamente o quantificador existencial (∃). Já o quantificador universal (∀) é formulado via dupla negação com as Leis de De Morgan: NOT EXISTS (... WHERE NOT ...).

Lógica Trivalente (3VL): Por que ela existe e o que é UNKNOWN?

Na lógica clássica proposicional, toda sentença é estritamente Verdadeira (TRUE) ou Falsa (FALSE) — o chamado Princípio do Terceiro Excluído. Contudo, em bancos de dados relacionais reais, informações do mundo físico podem estar ausentes, incompletas ou não preenchidas (ex.: um cliente que não cadastrou seu telefone).

Para lidar com dados ausentes, o SQL introduziu o marcador NULL (que não é um número nem um texto, mas um estado de ausência). Ao avaliar um predicado como salario > 5000 para um registro cujo salário é desconhecido, o motor não pode afirmar com certeza nem que é TRUE nem que é FALSE. Surge então a necessidade da Lógica Trivalente de Kleene (3VL), que introduz um terceiro valor lógico de verdade: o UNKNOWN (indeterminado).

Atenção para a distinção fundamental: NULL é um marcador de dados ausentes em colunas, enquanto UNKNOWN é um valor de verdade lógico booleano. Em SGBDs como o PostgreSQL, o tipo de dado BOOLEAN implementa 3 estados: true, false e null (onde o valor lógico UNKNOWN é exibido textualmente na saída como null).

Consultas reais no PostgreSQL demonstrando expressões avaliadas como UNKNOWN:
SELECT (1 = NULL); -- Resultado exibido: null (valor lógico: UNKNOWN)
SELECT (NULL = NULL); -- Resultado: null (não é true! Duas incógnitas não são iguais)
SELECT NOT(NULL); -- Resultado: null (a negação do desconhecido segue desconhecida)
SELECT true AND NULL; -- Resultado: null (pois depende do valor desconhecido)
SELECT false AND NULL; -- Resultado: false (falso com qualquer coisa no AND é false)

2. Contratos de Software: Design by Contract (DbC)

Criado por Bertrand Meyer na linguagem Eiffel, o paradigma Design by Contract (DbC) estabelece que a interação entre módulos de software é governada por um contrato formal baseado na implicação lógica:

Pré-condição (P) ⇒ Pós-condição (Q) ∧ Invariante de Classe (I)
require Pré-condição

Obrigações do chamador (cliente). Se a pré-condição for falsa, o método não é obrigado a executar e lança exceção imediata.

Ex: valor_saque > 0 ∧ saldo ≥ valor_saque
ensure Pós-condição

Garantias do fornecedor (método) ao término da execução, desde que a pré-condição tenha sido respeitada.

Ex: saldo == saldo_anterior - valor_saque
invariant Invariante

Predicado universal (∀) sobre o estado do objeto ou loop. Deve ser verdadeiro antes e depois de qualquer operação pública.

Ex: limite_cheque_especial ≥ 0
